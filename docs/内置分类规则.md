# 内置分类规则说明

对应实现：`mail-worker/src/utils/builtin-rules.js`（提交 `f4e3654` 起）。
接入位置：`mail-worker/src/email/email.js` 收信链路，位于用户过滤器之后、AI/本地兜底之前。

本文只描述已实现的行为，不包含准确率结论。

## 1. 五类定义与边界

| 类别 | 该收什么 | 不该收什么 |
| --- | --- | --- |
| 主要 primary | 人与人之间的邮件、带回复链的对话、没有明确自动化特征的普通邮件 | 平台通知、营销、订单/验证码 |
| 社交 social | 社交平台的关注、评论、提及、私信、邀请类通知 | 平台发的营销活动、广告 |
| 推广 promotion | 批量订阅/营销邮件：可退订、含促销词、由 ESP 代发 | 订单、发票、验证码等事务通知 |
| 动态 updates | 事务与系统通知：订单、发货、发票、账单、验证码、密码重置、自动生成的通知 | 带促销目的的“订单营销”邮件 |
| 垃圾 spam | 强垃圾内容且 SPF/DMARC 同时失败；以及原有 `blockFlag` 命中的邮件 | 普通营销邮件（应进推广） |

边界约定：

- 有 `In-Reply-To` 或 `References` 的邮件一律视为人工对话，直接判主要，不再参与推广/垃圾计分（`blockFlag` 仍最高优先）。
- 订单类邮件同时出现促销词时，用事务词给推广减分，让动态优先（见第 3 节）。
- 邮件列表/论坛没有独立类别，`List-Id` 不参与判定，避免把列表邮件误塞进动态。

## 2. 规则总表

动作说明：**直判**＝命中即返回该类别；**+N/−N**＝累加到该类别分数，最后与阈值比较。

| 编号 | 类别 | 匹配条件（字段/邮件头） | 判定动作 | 规则意图 |
| --- | --- | --- | --- | --- |
| R0-REPLY | 主要 | `In-Reply-To` 或 `References` 非空（优先读顶层字段，缺失时读同名邮件头） | 直判 primary | 人工对话优先，压制推广词与垃圾词误伤 |
| R1-SOCIAL-DOMAIN | 社交 | `From` 域名精确命中平台表，或为其子域名（facebook/facebookmail/instagram/linkedin/x.com/twitter/tiktok/pinterest/reddit/discord/slack/telegram/weibo/zhihu/douyin/xiaohongshu） | 直判 social | 平台官方发件域名是最稳定信号 |
| R2-SOCIAL-NAME | 社交 | 主题或正文出现平台名 | +2 | 非官方域名时的辅助信号 |
| R3-SOCIAL-COPY | 社交 | 主题或正文含互动文案（new follower / commented on your / 新增粉丝 / 关注了你 等） | +2 | 与 R2 叠加才达阈值，避免单条泛化 |
| R4-ONE-CLICK | 推广 | `List-Unsubscribe-Post` 含 `One-Click` | +4 | RFC 8058 一键退订，批量营销最强信号 |
| R5-UNSUBSCRIBE | 推广 | 存在 `List-Unsubscribe`，且不是一键退订 | +3 | 订阅/批量邮件信号；与 R4 不重复累加 |
| R6-PROMO-SUBJECT | 推广 | 主题命中促销词（sale/discount/off/coupon/deal/限时/折扣/双11/秒杀 等） | +2 | 主题最能表达营销意图 |
| R7-PROMO-BODY | 推广 | 正文命中促销词（同一封只记一次） | +2 | 正文补充，防止主题过于中性 |
| R8-ESP-DOMAIN | 推广 | `From` 域名命中 ESP 表（mailchimp/sendgrid/mailgun/amazonses/klaviyo 等） | +2 | 代发平台是弱信号，需叠加 |
| R9-TRANSACTIONAL | 推广 | 主题或正文命中事务词（order/invoice/receipt/验证码/订单/发货 等） | −2 | 反向惩罚，避免订单通知被判成推广 |
| R10-AUTOMATED-SENDER | 动态 | `From` 本地部分命中 noreply/no-reply/notification/alert/billing/security/verify/accounts/orders/receipts 等（整串或用 `. _ - +` 切词后比对） | +2 | 自动化发件人通常只发事务通知 |
| R11-TX-SUBJECT | 动态 | 主题命中事务词 | +3 | 主题权重最高，验证码/订单通常写在主题 |
| R12-TX-BODY | 动态 | 正文命中事务词 | +1 | 单独不足阈值，需要与发件人/主题叠加 |
| R13-AUTO-SUBMITTED | 动态 | `Auto-Submitted` 以 `auto-generated` / `auto-replied` / `auto-notified` 开头（`no` 不算） | +3 | RFC 3834 自动生成标记 |
| R14-SPAM-TERM | 垃圾 | 主题或正文命中强垃圾词（viagra/casino/博彩/代开发票/刷单 等） | +2 | 只作辅助，单独到不了阈值 |
| R15-AUTH-FAIL | 垃圾 | `Authentication-Results` 或 `ARC-Authentication-Results` 中 `spf=fail` **且** `dmarc=fail` | +3 | 双认证失败才与强词叠加成垃圾 |

英文词按单词边界匹配（`sale` 不会命中 `wholesale`，`off` 不会命中 `office`）；中文词按子串匹配。

## 3. 阈值与同分优先级

| 类别 | 阈值 |
| --- | --- |
| social | 4 |
| promotion | 4 |
| updates | 4 |
| spam | 5 |

决策：取达到阈值且分数最高的类别；同分时按 `spam > updates > promotion > social` 取前者。

**为什么动态优先于推广**：订单确认、发货、发票、验证码这类邮件的主题里经常同时出现营销词，如果按“推广分数高者胜”，会把真正的事务通知抢走。因此：

1. 事务词给推广 −2；
2. 同分时动态排在推广前面。

例：一封带 `List-Unsubscribe` 的订单通知，推广约 3−2=1 分，动态约 2+3=5 分，最终判动态；而“订单营销”邮件（限时优惠 + 订单字样 + 退订头）推广约 5 分、动态约 3 分，最终判推广。

## 4. 垃圾维度为什么故意收紧

- `blockFlag`（黑名单命中、`X-Spam-Status`、主题 `[spam]` 等现有逻辑）完全不动，仍是最高优先级。
- 新规则里 R14 只有 +2，阈值是 5，**单独永远不够**；R15 只有 +3，也单独不够。只有“强垃圾词 + SPF/DMARC 双失败”同时成立才刚好 5 分。
- 这是刻意设计，不是功能没做完：目的是不把现有垃圾判定放宽，避免营销邮件、海外转发邮件被误杀。想让垃圾更激进，应该先调 `SPAM_TERMS` 和 `THRESHOLDS.spam`，并自行承担误判风险。

## 5. 误判纠正路径

1. 网页端把邮件改到正确分类 → `mail-worker/src/service/email-service.js` 的 `learn()`。
2. 写入两张学习表：
   - `user_mail_rule`：按发件人记录类别；
   - `user_mail_rule_kw`：按“发件人 + 主题关键词”记录类别。
3. 下次收信时 `mailRuleService.categoryFor()` 先查学习规则，命中则直接使用。链路顺序是：
   `blockFlag → 学习规则 → 用户过滤器 → 内置规则 → AI/本地兜底`。
   因此**学习规则优先于内置规则**，用户改成“主要”即可永久压制该发件人的自动判定。
4. **学习不回改历史邮件**：`learn()` 只写规则表，不会批量重判已入库邮件；历史邮件需要手动重新分类才会更新。

## 6. 调参指引

所有可调内容都在 `mail-worker/src/utils/builtin-rules.js` 第 10–79 行（`// 可调参数` 区）：

| 位置 | 内容 | 说明 |
| --- | --- | --- |
| `THRESHOLDS` | 四个阈值 | 调高更保守，调低更激进 |
| `SOCIAL_DOMAINS` | 社交平台域名 | 精确/子域匹配，新增平台只加域名 |
| `SOCIAL_NAMES` / `SOCIAL_COPY` | 平台名、互动文案 | 两者各 +2，叠加才达 4 |
| `PROMO_TERMS` | 促销词 | 主题与正文各取首个命中 |
| `TRANSACTIONAL_TERMS` | 事务词 | 同时用于推广减分与动态加分 |
| `AUTOMATED_LOCAL_PARTS` | 自动化发件人本地部分 | 整串或切词比对 |
| `ESP_DOMAINS` | ESP 发信域名 | 弱信号 |
| `SPAM_TERMS` | 强垃圾词 | 只作辅助 |

权重写在规则主体里（`R0`–`R15` 的 `add()` 调用），如 `add('promotion', 3, 'R5-UNSUBSCRIBE', ...)`。改完必须跑：

```bash
node mail-worker/scripts/check-builtin-rules.mjs
```

脚本用 20 封构造邮件覆盖五类与边界场景，输出每封的判定、分数与命中规则；有不符合预期会以非 0 退出。脚本零依赖，不在生产包依赖图内。

## 7. 已知限制

- **没有真实邮件样本，也没有准确率实测数字**。20 条构造用例只验证“规则是否按预期触发”，不能换算成准确率或百分比。
- 规则是通用词表，未针对特定行业、语言分布或本实例的真实收信结构调优。
- `Auto-Submitted`、`List-Unsubscribe`、`Authentication-Results` 等信号只在收信时从内存邮件头读取；数据库只持久化了 `list_unsubscribe` / `list_unsubscribe_post`，因此**手动重新分类**（`classifyInbox`）用不到其余邮件头信号。
- ESP 域名表是本地手工维护，不来自某个可核实的公开清单，可能过时或缺失。
- 内置规则不产生 `ads` 类别；原兜底逻辑仍可能产生，属于遗留行为。
- 未新增依赖、未改表结构、未加迁移。

## 8. 发件人入参修复

修复前，`email.js` 把 PostalMime 的原始邮件对象直接传给 `classifyByRules()` 与 `classifyEmail()`，而两者签名要求 `{ name, sendEmail, subject, text }`。结果：

- `name` / `sendEmail` 恒为 `undefined`，`from` 拼出来是空串；
- 社交平台域名判断（`classifyByRules` 第 36 行）**永远不成立**；
- 自动化发件人判断（第 50 行）**永远不成立**，`updates` 只能靠主题里的验证码/订单词命中；
- AI 分类的 prompt 渲染成 `From:  <>`，模型看不到发件人。

修复后，`email.js` 先构造 `classifyInput`，再交给内置规则的兜底与 AI；上述判断恢复生效，AI 输入也带上真实发件人。这也是“线上分类不准”的主要原因之一：发件人维度此前在收信时整体失效。
